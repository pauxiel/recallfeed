## 2. Timing evidence and causal explanation

**Not a slow runner.** The runner image (`ubuntu-24.04` 20261103.629) and agent (2.338.2) are identical in all runs. CPU-bound steps match the green runs: install 6-7 s, lint 2-3 s, build 5-8 s, typecheck 20-22 s. Only the steps that use Docker and the database were slower: starting the database 29-31 s versus 23-25 s, and the test step 134-135 s versus 92-98 s.

**Each seed took about the same, as measured locally.** The failing test makes **25 database HTTP requests**: four `seedCard` calls at 6 requests each (an import's 5 plus an `UPDATE`), and one feed read. I timed every request and cross-checked my count against the database package's own `countHttpRequests` (6 and 6, 1 and 1: no hidden retries):

| Phase | Wall time | DB requests | Time outside the DB call |
|---|---|---|---|
| each seed (import + `UPDATE`) | about 460 ms | 6 | 0-3 ms |
| four seeds | about 1.85 s | 24 | about 0 |
| the feed request and assertions | about 78 ms | 1 | 1-3 ms |

**Where the time goes.** There were no lock waits (`pg_stat_activity`: none waiting during runs), no retries, and no work in the application between requests. The feed query executes in **0.07 ms** inside PostgreSQL (`EXPLAIN ANALYZE`), yet `select 1` through the local proxy takes **78-89 ms** (median 80 over 20), against about 40 ms through `docker exec psql`. So the cost is a fixed round trip in the proxy per request, and not query work.

**Explanation.** A test's duration is (its database requests) x (latency of one request). The test with the most requests (25) crosses Vitest's 5 s default first when the latency grows from about 80 ms locally to about 116-145 ms (green CI) and 196-256 ms (red CI). The model fits the red run's other multi-seed tests (4.65-4.86 s).

**Reproduction (tests the explanation, not just fits it).** With a temporary shim adding a delay only to requests for the local proxy, and no code change, the unmodified test took 2.0 s (+0 ms), 3.6 s (+60), 4.7 s (+100), and **timed out at 5,007 ms at +150 ms (about 230 ms per request)**, with sibling tests at 4.68 s, matching the red CI run. With the timeout lifted for measurement only, the slowest test took 6.2 s at about 230 ms per request and 10.5 s at about 380 ms.

## 3. The correction and why its scope is sufficient

**Change (6 test files, +30/-7; `tasks/todo.md` is the only non-test file in the PR):**
- `DATABASE_TEST_TIMEOUT_MS = 30_000` in `packages/api/src/__tests__/helpers.ts` and `packages/feed-engine/src/__tests__/helpers.ts`, with a comment giving the measurements.
- Applied as a **per-suite** `{ timeout }` option on the database-backed top-level `describe`: api `feed`, `feed-item`, `import`, and feed-engine `feed-engine`.

**Why 30 s, and why this scope.** 30 s is about three times the slowest measured case (10.5 s at about 380 ms per request, which is worse than anything observed in CI) and still stops a test that is truly stuck. Only the suites that make many requests per test needed it. The `database` package is untouched: its slowest red-run test was 2.4 s, and its slow tests are deliberate lock-wait tests. Assertions, the 80% coverage thresholds, database safety and serial execution are unchanged. Nothing is global, retried, or skipped, and no application code changed.

**Verified locally before pushing:**
- The option is enforced: with the constant temporarily set to 1 s, exactly the four seeded feed tests fail with `timed out in 1000ms`. Restored and compared.
- The failing test now passes at +150 ms (6.5 s) and at +300 ms (10.5 s), with all 77 database-backed API tests passing in both.
- Full gate on this branch from a clean state: lint 0, build 0 (5 of 5, 0 cached), typecheck 0, the 9 checker controls pass, and `pnpm test:coverage` runs **28 files, 422 tests, 0 skipped, 0 failed**, coverage **96.09 / 91.98 / 98.21 / 95.97** (threshold 80% each).
